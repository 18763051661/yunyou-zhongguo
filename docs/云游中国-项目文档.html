1. 项目概述

为什么做这个项目 · 解决什么问题 · 做到什么程度

1.1 立项背景

旅行决策场景中普遍存在三个痛点：① 攻略信息真假难辨，"照骗"泛滥；② 景点信息分散，行程规划耗时；③ 无法在出行前直观感受景区实景。本项目旨在构建一个数据真实、体验沉浸、决策智能的一站式旅游导览平台。

1.2 项目定位

「云游中国」是一个基于 SSM 框架（Spring + Spring MVC + MyBatis）的全国景点智能导览系统，覆盖 31 个省份的 219 个真实景点，提供景点导览、智能推荐、AI 行程规划、VR 360° 实景游览、在线购票支付、管理后台等完整功能闭环。

1.3 设计原则

数据真实

所有景点数据来自真实整理，杜绝假数据；AI 讲解受 RAG 约束，只允许基于库内真实景点作答，从源头防止幻觉。

架构规范

严格遵循 SSM 五层架构（Controller → Service → DAO → Mapper → MySQL），注解驱动零 XML，IoC / DI / AOP / 声明式事务全量应用。

体验沉浸

纯 CSS 3D 实现真 360° 全景环景舱，配合实拍六面贴图、AI 语音讲解与主题配乐，出行前即可"云游"景区。

链路完整

购票 → 支付 → 出票 → 退款全流程闭环，事务状态机保证数据一致，双通道支付架构支持扩展。

4.3 建表与初始化策略

  • 幂等建表：全部使用 CREATE TABLE IF NOT EXISTS，AppConfig 启动自举时自动校验建表，空库自动灌入种子数据，一次启动即可运行；

  • 查询优化：省份/评分/热度榜高频查询建立索引；热度榜通过 vr_view_log 聚合（GROUP BY + COUNT）实现。

6. 景点导览与智能推荐

高频查询的安全与性能设计

6.1 多条件动态查询

支持关键字、省份、价格带、主题标签组合筛选，排序字段（评分/热度/价格）由 Service 层白名单映射后传入 SQL，从根本上杜绝排序注入。

// SpotMapper —— MyBatis 注解 + 动态 SQL
@Select("<script>SELECT * FROM scenic_spot WHERE status = 1" +
  "<if test='kw != null'> AND (name LIKE CONCAT('%',#{kw},'%'))</if>" +
  "<if test='province != null'> AND province = #{province}</if>" +
  " ORDER BY ${safeSort} LIMIT #{offset}, #{size}</script>")
安全设计：#{ } 预编译防注入；${safeSort} 仅接收白名单映射值（rating/hot/price），用户输入永不直接拼接 SQL。

6.2 手写物理分页

不依赖 PageHints 插件，直接 LIMIT offset,size + COUNT 双查询，返回 {list, total, page, size} 结构，前端据此渲染分页条。

6.3 智能推荐策略

热门推荐

按 vr_view_log 打卡热度聚合排序，真实用户行为驱动

高分精选

评分 ≥ 4.5 且评论数达标的景点池，保证口碑

偏好匹配

用户勾选的自然/人文/美食等标签与景点 tag 求交集加权

6.4 景点图片流水线

每个景点配真实图片：图片搜索 → 标题相关性匹配 → MD5 去重 → 服务端压缩 → 本地缓存。加载失败自动降级 picsum.photos/seed/{spotId} 稳定源，保证任何网络环境下页面不破图。

7. 智能出游规划器

8 字段偏好问卷 → AI 生成个性化路线 → 持久化落库

7.1 交互流程

用户填写问卷（目的地省份 / 出行天数 / 同行人 / 预算 / 偏好主题 / 节奏 / 交通方式 / 特殊要求）
 → POST /api/plan  → PlanService.generate()
 → 组装 Prompt：RAG 注入该省真实景点数据（名称/评分/价格/坐标）
 → AI 四引擎依次尝试（DeepSeek → 通义 → 豆包 → 本地规则）
 → 解析结构化路线（Day1~DayN，含景点/顺序/理由）
 → 落库 travel_plan 表 → 返回前端渲染时间轴

7.2 RAG 约束提示词（核心）

系统提示词要点：
1. 你只能从下方【候选景点列表】中选择景点，禁止编造任何不存在的景点
2. 每天安排 2-4 个景点，标注每个景点的推荐理由与预估花费
3. 输出严格 JSON 格式：{days:[{day, spots:[{name, reason, cost}]}]}
4. 候选数据（来自 MySQL，共 N 条）：[{"name":"九寨沟","rating":4.8,...}]

7.3 工程细节

  • 超时分级：DeepSeek 10s / 通义 8s / 豆包 15s，超时即切换下一引擎，总失败兜底本地规则；
  • 结果缓存：相同省份 + 偏好组合的规划结果落库复用，二次请求毫秒级返回；
  • 双消费方式：SPA 走 REST API，JSP 页面走 @ModelAttribute 表单绑定，同一 Service 两种呈现。
实测：qwen-turbo 生成 5 日路线约 3.9s；DeepSeek 生成质量最高但需 8~10s——引擎分级正是质量与速度的权衡设计。

9. 票务订单与事务状态机

@Transactional 原子流转 · 幂等保护 · 一致性保证
PENDING 待支付
──支付──▶
PAID 已支付
──退款──▶
CANCELED 已取消

9.1 状态机实现

@Transactional  // OrderServiceImpl —— 状态流转原子性
public void markPaid(String orderNo) {
    int rows = orderDao.casUpdateStatus(orderNo, "PENDING", "PAID");
    // CAS 式 UPDATE：UPDATE ticket_order SET status='PAID'
    //               WHERE order_no=? AND status='PENDING'
    if (rows == 0) throw new IllegalStateException("状态冲突/重复支付");
}
幂等保护：CAS 条件更新保证同一订单并发重复回调只生效一次；非法流转（如 CANCELED → PAID）被状态条件天然拒绝。

9.2 订单功能矩阵

功能说明
下单生成唯一 order_no，金额服务端计算（不信前端），初始 PENDING
支付确认三通道（支付宝/微信/沙箱模拟）统一收敛到状态机 markPaid
主动补单回调不可达时（校园网无公网），前端轮询触发 trade.query 主动对账
退款 / 删除PAID → CANCELED（@Transactional）；删除为逻辑删除，审计可溯

9.3 票根式凭证

已支付订单生成票根 UI：左侧票存（景点名/金额/单号）+ 打孔虚线分割 + 右侧信息区 + 二维码电子凭证，视觉上模拟真实景区门票，细节拉满。

10. 双通道支付架构

10.1 架构设计

OrderController.pay(method)
 ├─ ALIPAY → AlipayPayService（真实沙箱：RSA2 签名 / wap.pay 下单 / trade.query 对账 / notify 验签）

10.2 支付宝沙箱真实对接

10.3 设计价值

  • 策略模式：新增渠道（如云闪付）只需新增一个 Service 实现 + 一个分支，状态机零改动；

12. RAG 数据约束 与 AOP 零侵入审计

让 AI 只说真话 · 让审计零侵入

12.1 RAG 数据约束（防幻觉）

AI 幻觉是旅游类应用最大风险——编造不存在的景点会直接毁掉可信度。本项目的解法：

  • 召回：按用户问题/规划条件，从 MySQL 219 个真实景点中检索候选集；
  • 注入：候选集结构化注入 System Prompt，并施加硬约束——"只能从候选列表选择，禁止编造"；
  • 校验：AI 输出中的景点名回库校验，不在库内的条目剔除并降级重试；
  • 兜底：全部失败时返回本地规则结果，前端徽章如实标注来源引擎。
效果：AI 讲解、智能规划、一句话游记的全部内容都可回溯到数据库真实景点——「数据是真的」贯穿全项目。

18.2 收获

  • 架构能力：理解了 IoC/DI/AOP/事务在真实业务中的落位，而非停留在概念；
  • 工程判断：AI 引擎选型、超时分级、通道降级——每个决策都由实测数据驱动；
  • 问题闭环：从「发现坑」到「填坑」到「讲清楚为什么这样填」，完成完整训练。

18.3 展望
